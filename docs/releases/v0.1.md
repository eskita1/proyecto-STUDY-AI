# StudyAI V0.1

**Status:** In progress

## 1. Objective

V0.1 establishes StudyAI's first functional backend for source-backed academic structure and student-controlled study tracking.

The release must represent the path from an institution and StudyPlan to a concrete CourseOffering, allow validated academic structure to be shared only by students in that offering, and keep each student's progress, Study, and Practice records independent.

The interface is API-only. A frontend is outside V0.1.

## 2. Technical scope

V0.1 retains the project's backend foundation:

- FastAPI;
- PostgreSQL;
- SQLAlchemy;
- Alembic migrations;
- configuration through environment variables;
- automated tests;
- Ruff;
- CI with GitHub Actions;
- Swagger/OpenAPI access to included API behavior.

## 3. Functional scope

V0.1 includes:

- institutional structure from University through StudyPlanCourse;
- abstract Courses separated from their StudyPlan placement;
- concrete CourseOfferings identified by chair or section and academic period or year;
- source-backed Units, Topics, and Subtopics;
- extraction, proposal, validation, and confirmation boundaries for academic structure;
- UserCareer, historical UserCourse, and concrete CourseEnrollment relationships;
- per-enrollment Topic progress and personal study state;
- StudySessions in quick and full modes;
- PracticeSessions in quick and detailed modes;
- Course schedule items;
- Assessments and their Topic associations;
- derived course, student, and catch-up progress metrics.

## 4. Institutional and delivery model

The institutional structure is:

```text
University -> Faculty -> Career -> StudyPlan -> StudyPlanCourse
```

`Course` is an abstract course concept. `StudyPlanCourse` represents that Course inside a specific StudyPlan.

Concrete delivery is:

```text
StudyPlanCourse -> CourseOffering -> Unit -> Topic -> Subtopic
```

`CourseOffering` represents a specific chair or section in a specific academic period or year.

Students share academic structure only when they belong to the same CourseOffering.

## 5. Academic sources and confirmed structure

Users do not freely create or edit Units, Topics, or Subtopics. Those entities must be based on academic material supplied by a User, chair, or University.

V0.1 supports these AcademicSource types:

- `STUDY_PLAN`
- `SYLLABUS`
- `SCHEDULE`
- `THEORETICAL_MATERIAL`
- `PRACTICE_MATERIAL`
- `OTHER`

An AcademicSource has one of these statuses:

- `PENDING`
- `CONFIRMED`
- `SUPERSEDED`

The required processing boundary is:

```text
source -> extraction -> proposed structure -> validation -> confirmed domain
```

AI may assist with extraction and proposed structure. It must never write directly into the confirmed academic domain.

Subtopics may originate only in sources supplied by a User, chair, or University. AI must not invent them from general model knowledge.

Units and Topics have one of these statuses:

- `ACTIVE`
- `REMOVED`

Removed Units and Topics must remain stored; removal is not physical deletion.

Every Topic belongs to exactly one Unit. Every Subtopic belongs to exactly one Topic.

## 6. Student model

The User relationships are:

```text
User -> UserCareer
User -> UserCourse -> CourseEnrollment -> EnrollmentTopic
```

`UserCourse` is the historical relationship between a User and a StudyPlanCourse.

`CourseEnrollment` represents one concrete attempt or enrollment in a CourseOffering and includes conceptually:

- `user_course_id`
- `course_offering_id`
- `status`
- `final_grade`

Supported statuses are:

- `IN_PROGRESS`
- `PASSED`
- `FAILED`

`RETAKING` and `DROPPED` are outside V0.1.

`EnrollmentTopic` includes conceptually:

- `course_enrollment_id`
- `topic_id`
- `course_progress_status`
- `student_status`
- `personal_note`

Course progress status is:

- `NOT_SEEN`
- `SEEN`

Student status is:

- `NOT_STARTED`
- `IN_PROGRESS`
- `STUDIED`

The User manually controls both actual course progress and personal study state. StudyAI must not automatically change `student_status`.

The User may move freely between student states, including backwards. `STUDIED` means the User considers the Topic studied; it does not imply Practice or Mastery. Only `STUDIED` counts as completed for student-progress metrics.

Scheduled dates do not automatically imply `SEEN`.

If a Topic later becomes `REMOVED`, the User's existing personal state must be preserved.

## 7. Study activity

`StudySession` belongs to a CourseEnrollment and includes conceptually:

- `course_enrollment_id`
- `started_at`
- `ended_at`, nullable
- `note`

`StudySessionTopic` associates StudySessions with Topics.

V0.1 supports:

- quick mode without an end time;
- full mode with start and end times.

Creating a StudySession must not automatically change `student_status`.

`last_studied_at` is derived from the latest related StudySession and must not be stored redundantly as a source of truth.

## 8. Practice

`PracticeSession` belongs to a CourseEnrollment and includes conceptually:

- `course_enrollment_id`
- `occurred_at`
- `source_type`
- `source_name`
- `note`

`PracticeSessionTopic` associates PracticeSessions with Topics.

Quick mode includes:

- `total_exercises`
- `correct_exercises`
- `partial_exercises`
- `incorrect_exercises`

Detailed mode uses `PracticeExercise` with:

- `practice_session_id`
- `label`
- `result`

Supported results are:

- `CORRECT`
- `PARTIALLY_CORRECT`
- `INCORRECT`
- `NOT_EVALUATED`

Practice is independent from Progress and must not automatically modify `student_status`.

Mastery remains separate and is outside V0.1.

## 9. Time and assessments

`CourseScheduleItem` includes conceptually:

- `course_offering_id`
- `scheduled_date`
- `unit_id`, optional
- `topic_id`, optional
- `position`

Schedule dates represent plans, not confirmed events, and never automatically mark Topics as `SEEN`.

`Assessment` includes conceptually:

- `course_offering_id`
- `name`
- `type`
- `date`
- `description`

Supported Assessment types are:

- `MIDTERM`
- `FINAL`
- `RECOVERY`
- `ASSIGNMENT`
- `QUIZ`
- `OTHER`

`AssessmentTopic` associates Assessments with Topics.

## 10. Derived metrics

The following metrics are calculated from confirmed structure and EnrollmentTopic state. They must not be stored as independent sources of truth.

```text
active_topics = topics where status != REMOVED
course_progress = SEEN / active_topics
student_progress = STUDIED / active_topics
catch_up_progress = SEEN_AND_STUDIED / all_SEEN
```

Only `STUDIED` counts as completed for student progress.

## 11. API and persistence constraints

Included behavior must:

- be exposed through explicit API input and output models where API access is provided;
- use appropriate HTTP status codes and consistent errors;
- keep HTTP, application, persistence, and database responsibilities separate;
- persist through SQLAlchemy and PostgreSQL;
- change database structure only through Alembic migrations;
- be usable through Swagger/OpenAPI.

Academic-structure write behavior must preserve the source, proposal, validation, and confirmation boundary. A generic direct CRUD path must not allow AI or Users to bypass that boundary for confirmed Units, Topics, or Subtopics.

## 12. Testing and quality

Tests must cover the included capabilities and their essential relationships and invariants, especially:

- CourseOffering isolation of shared academic structure;
- the AcademicSource confirmation flow;
- Unit and Topic removal without physical deletion;
- Topic and Subtopic ownership;
- CourseEnrollment statuses;
- manual EnrollmentTopic state changes, including backwards transitions;
- preservation of personal state for removed Topics;
- StudySession quick and full modes without automatic student-state changes;
- PracticeSession quick and detailed modes without automatic student-state changes;
- schedule dates without automatic `SEEN` transitions;
- AssessmentTopic associations;
- derived metrics excluding removed Topics where required.

Required checks remain:

```bash
pytest
ruff check .
```

CI must run tests and Ruff on pushes and pull requests.

## 13. Out of scope

V0.1 does not include:

- authentication or authorization;
- a frontend;
- `RETAKING` enrollment status;
- `DROPPED` enrollment status;
- Mastery;
- automatic `student_status` changes from any system event;
- automatic `SEEN` changes from schedule dates;
- direct AI writes to confirmed academic structure;
- Subtopics invented by AI from general model knowledge;
- physical deletion of removed Units or Topics;
- stored copies of derived progress metrics or `last_studied_at` as sources of truth.

## 14. Acceptance criteria

V0.1 is functionally complete when it is possible to:

1. represent University, Faculty, Career, StudyPlan, Course, and StudyPlanCourse;
2. create a concrete CourseOffering for a chair or section and academic period or year;
3. provide AcademicSources and move extracted proposals through validation into confirmed structure;
4. represent confirmed Units, Topics, and source-backed Subtopics;
5. mark Units or Topics as `REMOVED` without deleting them;
6. associate a User with a Career, StudyPlanCourse history, and concrete CourseEnrollment;
7. maintain User-controlled course progress and personal study state per Topic;
8. preserve that personal state when a Topic is removed;
9. record quick and full StudySessions without automatic status changes;
10. derive the latest study time from StudySessions;
11. record quick and detailed PracticeSessions without automatic status changes;
12. represent planned schedule items without treating plans as confirmed progress;
13. represent Assessments and associate them with Topics;
14. derive course, student, and catch-up progress from authoritative state;
15. exercise included API behavior through Swagger/OpenAPI;
16. apply migrations successfully;
17. pass automated tests and Ruff in CI.

## 15. Definition of Done

V0.1 is complete when all included behavior and invariants are implemented, migrations are reproducible, tests and Ruff pass, CI is green, the API can be exercised through Swagger/OpenAPI, relevant documentation matches the behavior, and no blocking product or domain decision remains unresolved.
