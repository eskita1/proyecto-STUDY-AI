# StudyAI V0.1

**Status:** In progress

## 1. Objective

Build the first functional version of the StudyAI backend.

V0.1 must combine a solid technical foundation with a minimal academic representation sufficient to test the product's main flow through the API.

The release must support simulating a University student who records their University, Faculty, Career, StudyPlan, and Courses.

The interface will be API-only. The frontend is out of scope.

---

## 2. Scope

V0.1 includes:

- FastAPI backend;
- PostgreSQL;
- SQLAlchemy;
- Alembic;
- configuration through environment variables;
- automated testing;
- Ruff;
- CI with GitHub Actions;
- foundational project documentation;
- initial academic entities;
- real persistence;
- complete CRUD for the specified included entities, with the documented User exception;
- endpoint exposure and testing through Swagger/OpenAPI.

---

## 3. Minimum entities

### User

Represents the student.

V0.1 does not require authentication.

It must exist as a persistent entity so academic information can be associated with a specific student.

### University

Represents a University.

### Faculty

Represents a Faculty or academic unit that belongs to a University.

### Career

Represents a University Career.

It must be associated with a Faculty.

### StudyPlan

Represents a specific version of a Career's StudyPlan.

It must allow the same Career to eventually have more than one StudyPlan.

### Course

Represents an academic Course as an independent concept.

At minimum, it must be able to store:

- name;
- identifier.

CourseStatus and `final_grade` do not belong to Course.

### StudyPlanCourse

Represents the relationship between a StudyPlan and a Course.

It allows a Course to appear in one or more StudyPlans and stores information specific to that Course's placement in a StudyPlan.

### UserCareer

Represents the relationship between a User and a Career, including the StudyPlan selected by that User for the Career.

### UserCourse

Represents the academic relationship between a User and a Course.

It stores:

- the User's CourseStatus;
- `final_grade` when applicable.

---

## 4. CourseStatus

In V0.1, a UserCourse must have one of these states:

- `approved`
- `active`
- `future`

### Approved

The User has taken and passed the Course.

The UserCourse may have an associated `final_grade`.

### Active

The User is currently taking the Course.

### Future

The Course belongs to the User's academic journey but has not yet been taken.

CourseStatus belongs to UserCourse, not Course.

---

## 5. final_grade

An approved UserCourse may store a `final_grade`.

`final_grade` belongs to UserCourse, not Course.

Exact grade-range validation may depend on the academic system in use and must remain simple in V0.1.

Do not add complex equivalency or international grading-scale logic in this release.

---

## 6. StudyPlan

V0.1 must support loading a real StudyPlan.

The expected flow is:

1. create a University;
2. create a Faculty;
3. create a Career;
4. create a StudyPlan;
5. create the corresponding Courses;
6. relate the Courses to the StudyPlan through StudyPlanCourse;
7. associate the User with the Career and selected StudyPlan through UserCareer;
8. create the relevant UserCourse relationships;
9. set CourseStatus on each UserCourse;
10. record `final_grade` values on approved UserCourse relationships where applicable.

Automated StudyPlan retrieval from external sources is not yet required.

Data may be loaded manually through the API.

---

## 7. CRUD

The following V0.1 entities must support complete CRUD:

- create;
- read;
- list;
- update;
- delete.

At minimum, this applies to:

- University;
- Faculty;
- Career;
- StudyPlan;
- Course;
- StudyPlanCourse;
- UserCareer;
- UserCourse.

User is an intentional exception in V0.1 and supports:

- create;
- read;
- update.

User deletion is out of scope for V0.1.

For entities with deletion in scope, deletion must be implemented simply and consistently with existing relationships.

---

## 8. API

The API must:

- follow reasonable REST conventions;
- use explicit input and output models;
- use appropriate HTTP status codes;
- validate input data;
- return consistent errors;
- keep HTTP, business, and persistence responsibilities separate.

Endpoints must be testable through Swagger.

No frontend is required.

---

## 9. Persistence

Persistence must use:

- PostgreSQL;
- SQLAlchemy;
- Alembic for migrations.

The database structure must be created and changed through versioned migrations.

Do not use manual table creation as the project's main mechanism.

---

## 10. Testing

Each main capability must have reasonable tests.

At minimum, tests must cover:

- health endpoint;
- creation of main entities;
- entity retrieval;
- updates;
- deletion;
- relevant validations;
- essential relationships.

Tests must run with:

```bash
pytest
```

---

## 11. Code quality

Ruff must run successfully with:

```bash
ruff check .
```

Do not add other quality tools without a concrete need.

---

## 12. CI

GitHub Actions must automatically run:

- dependency installation;
- tests;
- Ruff.

CI must run on:

- push;
- pull request.

V0.1 is not considered complete if CI fails.

---

## 13. Swagger / OpenAPI

All endpoints included in V0.1 must be usable and verifiable through FastAPI's automatic documentation.

The V0.1 demo must be possible through Swagger without additional external tools.

---

## 14. Out of scope

V0.1 does NOT include:

- authentication;
- authorization;
- login;
- passwords;
- JWT;
- OAuth;
- frontend;
- topics;
- CoursePace;
- Progress;
- Mastery;
- Practice tracking;
- exercise tracking;
- study recommendations;
- calendar;
- weekly planning;
- AI;
- PDF uploads;
- academic tutor;
- exercise generation;
- Course prerequisites;
- community;
- opinions about Courses.

These capabilities belong to later versions.

---

## 15. Acceptance criteria

V0.1 is considered functional when it is possible to:

1. start the backend successfully;
2. connect to PostgreSQL;
3. apply migrations;
4. create a User;
5. create a University;
6. create a Faculty;
7. create a Career;
8. create a StudyPlan;
9. relate Courses to the StudyPlan through StudyPlanCourse;
10. associate the User with the Career and selected StudyPlan through UserCareer;
11. create UserCourse relationships;
12. mark each UserCourse as `approved`, `active`, or `future`;
13. record a `final_grade` on approved UserCourse relationships;
14. retrieve information through Swagger;
15. modify it;
16. delete it where appropriate;
17. run all tests successfully;
18. run Ruff without errors;
19. complete CI successfully.

---

## 16. Target demo

The minimum V0.1 demo must represent a real case.

Example:

- create a User;
- record a University and Faculty;
- record a Career;
- load the real StudyPlan;
- create its Courses and relate them through StudyPlanCourse;
- associate the User with the Career and StudyPlan through UserCareer;
- create the relevant UserCourse relationships;
- mark some UserCourse relationships as approved with their `final_grade` values;
- mark some UserCourse relationships as active;
- leave the remaining UserCourse relationships as future;
- retrieve everything through Swagger;
- modify some data;
- verify that the endpoints work;
- verify that tests pass;
- verify that CI is green.

---

## 17. Definition of Done

V0.1 is complete when:

- all defined scope is implemented;
- no future functionality has been implemented accidentally;
- migrations are reproducible;
- the main endpoints work;
- tests pass;
- Ruff passes;
- CI passes;
- Swagger can test the API;
- relevant documentation is up to date;
- no blocking decisions remain open.

---

## 18. Open questions

These must not block V0.1 for now:

- exact format for Course identifiers;
- `final_grade` range;
- future Course prerequisite rules;
- topic structure;
- formal definition of Progress;
- formal definition of Mastery.

These decisions must be resolved when the corresponding version requires them.
